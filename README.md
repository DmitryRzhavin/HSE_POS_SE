# ПОС — Преподавательская Оценка Студентов

Консольное приложение на C++17: учёт студентов, рубрикатора и оценок, расчёт итога по весам и выгрузка в CSV.
Построено по DDD, архитектура — **Ports and Adapters (Hexagonal)**, зависимости направлены внутрь.
Данные хранятся в памяти до завершения процесса.

## Сборка и запуск (Ubuntu)

```bash
sudo apt update && sudo apt install -y build-essential cmake git
cmake -S . -B build
cmake --build build --parallel
./build/pos_app
```

Сквозной сценарий (студенты → критерии → оценки → исправление → итог → экспорт) запускается готовым вводом:

```bash
./build/pos_app < examples/demo_input.txt   # создаст report.csv в текущем каталоге
```

Тесты (GoogleTest подтягивается через CMake FetchContent, нужен доступ в интернет при первой сборке):

```bash
ctest --test-dir build --output-on-failure
# или напрямую: ./build/pos_tests
```

Импорт ведомости (пункт меню 11): форматы `csv` (`examples/sheet_comma.csv`) и `excel`
(`examples/sheet_excel.csv`, разделитель `;`, десятичная запятая). Ошибочные строки не прерывают импорт —
они попадают в отчёт с номером строки.

## Архитектура: Ports and Adapters

```
src/pos/
├── domain/          # ядро: entity, VO, инварианты, domain service (без I/O и UI)
├── application/     # сценарии (use cases), Facade и порты (интерфейсы наружу)
├── infrastructure/  # адаптеры: консоль, CSV-выгрузка, хранилища в памяти, системные часы
└── container.*      # composition root (DI-контейнер)
src/main.cpp         # точка входа
```

Стрелка зависимостей: `infrastructure → application → domain`. Порты (`StudentRepository`, `RubricRepository`,
`GradebookRepository`, `Clock`, `GradeReportWriter`) объявлены в `application/ports.hpp`, а реализованы в `infrastructure/`.
Домен не включает ни одного заголовка из верхних слоёв. Единственное место, знающее конкретные классы, — `container.cpp`.

## Карта DDD

| Понятие | Реализация | Тип |
|---|---|---|
| студент | `Student` | Entity (идентичность — `StudentId`) |
| критерий | `Criterion` (макс. балл, вес) | Entity внутри агрегата `Rubric` |
| рубрикатор | `Rubric` | Корень агрегата: уникальность критериев, `total_weight` |
| оценка | `Evaluation` | Entity (идентичность — пара студент + критерий) |
| балл | `Score` | Value Object: создаётся только `Score::of(value, criterion)`, вне диапазона не существует |
| идентификаторы | `StudentId`, `CriterionId` | Value Object |
| итог | `FinalGrade` | Value Object, вычисляется, а не хранится |
| ведомость | `Gradebook` | Корень агрегата: не больше одной оценки на (студент, критерий) |
| расчёт итога | `FinalGradeCalculator` | Domain Service |
| хранение | `StudentRepository`, `RubricRepository`, `GradebookRepository` | Repository (порты) |

Инварианты, которые охраняет модель:

- балл в диапазоне `[0, max_score]` критерия (`Score::of`);
- оценку можно создать только по критерию из рубрикатора (`EvaluationFactory`);
- в рубрикаторе нет двух критериев с одним id, максимум и вес положительны;
- у пары (студент, критерий) не больше одной оценки (`Gradebook`);
- итог всегда считается из текущих оценок и рубрикатора, отдельно его никто не задаёт.

Границы агрегатов: `Rubric` и `Gradebook` — разные агрегаты, они связаны по идентификатору критерия (`CriterionId`),
а не по ссылке. Существование студента при выставлении оценки проверяет application-слой (`GradingService`),
потому что `Student` живёт в собственном репозитории.

Entity vs Value Object на примере: два студента с одинаковым именем — разные люди (Entity, различает id);
два балла `8.0` взаимозаменяемы (Value Object, идентичности нет).

## Паттерны GoF

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | Factory | `EvaluationFactory::create` | Единственная точка создания `Evaluation`: конструктор приватный, поэтому оценку с неверным баллом или несуществующим критерием создать нельзя ни из UI, ни из импорта |
| Структурный | Facade | `PosFacade` | Консоль знает только один класс и не собирает вместе пять сервисов, репозитории и политики |
| Структурный | Decorator | `RoundingPolicy` над `GradingPolicy` | Округление добавляется к любому правилу итога без изменения самих правил; в контейнере собрана цепочка `RoundingPolicy(WeightedAveragePolicy)` |
| Поведенческий | Strategy | `GradingPolicy`: `WeightedAveragePolicy`, `GradedOnlyPolicy` | Правило итога меняется (невыставленные = 0 или не учитываются) без правки Domain Service; подмена — `Container::override_grading_policy` |
| Поведенческий | Template Method | `SheetImporter::import_sheet` | Каркас импорта (пропуск заголовка, применение через `GradingService`, сбор ошибок по строкам) общий; разный разбор у `CsvSheetImporter` и `ExcelCsvSheetImporter` |

Не использовались паттерны «для галочки»: например, Builder рубрикатора не нужен, так как критерии добавляются по одному
через `Rubric::add_criterion` без сложной сборки.

## Итог

Для каждого студента: `percent = Σ(вес_i · балл_i / max_i) / Σ вес_i · 100`. Шкала 10 баллов — `percent / 10`.
Стандартное правило (`WeightedAveragePolicy`) делит на сумму весов **всего** рубрикатора, поэтому критерий без оценки
считается нулём. `GradedOnlyPolicy` делит только на вес оценённых критериев и годится для промежуточного итога.

## DI и тестирование

`Container` — собственный лёгкий DI-контейнер на `std::shared_ptr` с внедрением через конструктор: создаёт зависимости
лениво, разделяет одни и те же репозитории между сервисами и позволяет подменить часы, политику итога и экспорт
(`override_clock`, `override_grading_policy`, `override_report_writer`). Сторонняя DI-библиотека не подключалась,
чтобы не усложнять учебный проект.

Тесты (`tests/`, GoogleTest):

- `test_domain.cpp` — инварианты (`Criterion`, `Rubric`, `EvaluationFactory`, `Gradebook`), расчёт `FinalGradeCalculator`, стратегии и декоратор;
- `test_application.cpp` — сценарии, дубликаты, исправление/отмена оценки, экспорт через фейковый порт, CSV-адаптер, импорт обоих форматов;
- `test_console.cpp` — сквозной сценарий и обработка ошибок ввода через `std::istringstream`/`std::ostringstream`;
- `test_container.cpp` — подмена зависимостей и общие репозитории.

## Ограничения

- Данные не сохраняются между запусками (хранилище в памяти); для постоянного хранения достаточно написать новые адаптеры
  портов-репозиториев, не трогая домен и сценарии.
- Один курс и один рубрикатор; пересдачи, апелляции и несколько курсов в модель не заложены.
